راهنمای گام‌به‌گام استقرار «میز رمز عبور»

تنظیم TrueNAS SCALE و راه‌اندازی سرویس روی یک سرور لینوکسی مستقل — نسخهٔ ۲۵ اکتبر ۲۰۲۶ — مخاطب: مدیر سیستم

این راهنما چه چیزی را پوشش می‌دهد: آماده‌سازی سرور TrueNAS SCALE (بررسی نسخه، کلید API، گواهی، حساب آزمایشی)، پیکربندی سرور لینوکسی، ساختن فایل .env، اجرای اسکریپت استقرار و کار روزمره با اپلیکیشن. همهٔ دستورها با $ شروع می‌شوند و باید در پوشهٔ اصلی پروژه اجرا شوند. مقادیر نمونه (مانند truenas.home.local) را با مقادیر واقعی خودتان جایگزین کنید.

قواعد امنیتی غیرقابل مذاکره: هر «پیوند» همانند یک رمز عبور است؛ هر کس پیوند معتبر و استفاده‌نشده را داشته باشد می‌تواند رمز آن حساب را تغییر دهد — بدون نیاز به رمز فعلی. کلید API باید دسترسی کامل مدیر (FULL_ADMIN) داشته باشد و بسیار قدرتمند است. هرگز مقدار کلیدها، رمزها یا پیوندها را در چت عمومی، تیکت، اسکرین‌شات یا خروجی ترمینال قرار ندهید. اعتبارسنجی گواهی TLS را هرگز غیرفعال نکنید.

خلاصهٔ معماری

این سرویس از سه سرویس داکری روی یک سرور لینوکسی مستقل تشکیل شده است: پایگاه‌دادهٔ PostgreSQL 17، اپلیکیشن Next.js و پروکسی Caddy که تنها درگاهِ روشن روی میزبان (۸۰/۴۴۳) است. اپلیکیشن از طریق WebSocket به wss://<nas>/api/current متصل می‌شود، با کلید API وارد می‌شود و user.set_password را بدون رمز قدیمی فرامی‌خواند. اتصال مرورگر کاربران هرگز مستقیم به TrueNAS نیست.

۱ بررسی پیش‌نیازهای TrueNAS

  1. در صفحهٔ اطلاعات سیستم TrueNAS نسخهٔ دقیق را بررسی کنید. فقط نسخه‌های 25.10.0 یا 25.10.7 از SCALE پشتیبانی می‌شوند — سایر نسخه‌های ۲۵.۱۰.x هم رد می‌شوند. CORE و کاربران AD/LDAP پشتیبانی نمی‌شوند.
  2. کاربران SMB باید محلی باشند (نه متصل به دامنهٔ Active Directory).
  3. دسترسی مدیریتی به رابط وب TrueNAS و شبکهٔ خصوصی بین دو سرور را داشته باشید.

۲ ساخت کلید API روی TrueNAS

  1. با حساب مدیر به رابط وب TrueNAS وارد شوید و به بخش مدیریت کلیدهای API بروید (در این نسخه از منوی سیستم قابل دسترسی است).
  2. یک کلید جدید بسازید. این کلید باید متعلق به یک حساب مدیر محلیِ اختصاصی باشد (فقط برای همین سرویس، نه حساب شخصی شما). سطح دسترسی لازم FULL_ADMIN است.
  3. اگر تنظیم انقضا در دسترس است، برای کلید انقضا تعیین کنید. کلید را یک‌بار کپی کنید و فقط در فایل .env سرور اپلیکیشن ذخیره کنید.
  4. یک حساب SMB محلیِ یک‌بارمصرف برای تست بسازید (مثلاً smb-test). با این حساب، کل سیر کار را قبل از تولید آزمایش می‌کنید.

این کلید می‌تواند هر کاربر محلی NAS را تغییر دهد. دسترسی شبکه‌ای به رابط مدیریت NAS را فقط به میزبان اپلیکیشن محدود کنید و کلید را در صورت مشکوک شدن به نفوذ، باطل/چرخش دهید. به کاربران عادی SMB نقش مدیریتی ندهید.

۳ گواهی HTTPS سرور TrueNAS

  1. اپلیکیشن با آدرس HTTPS به NAS وصل می‌شود و اعتبارسنجی گواهی همیشه روشن است. اگر از IP استفاده می‌کنید، گواهی باید آن IP را در SAN داشته باشد — گواهی پیش‌فرض خودامضای TrueNAS فقط localhost را پوشش می‌دهد و رد می‌شود.
  2. راه پیشنهادی: یک گواهی برای نام میزبان NAS از CA داخلی سازمانتان صادر کنید (مثلاً truenas.home.local) و روی NAS تنظیمش کنید.
  3. فایل گواهی عمومی CA داخلی را در پوشهٔ nas-ca/ پروژه با نام nas-ca.crt بگذارید؛ Compose آن را فقط‌خواندنی داخل کانتینر سوار می‌کند.

۴ آماده‌سازی سرور لینوکسی

  1. یک سرور لینوکسی (x64 یا arm64) با Docker و افزونهٔ Compose آماده کنید. این سرور یک سیستم مدیریتی محسوب می‌شود؛ مثل NAS از آن محافظت کنید.
  2. رکورد DNS نام عمومی سرویس (مثلاً password.example.local) را به همین سرور اشاره دهید. Caddy به‌طور خودکار گواهی می‌گیرد؛ برای نام‌های داخلی، پیکربندی CA خصوصی/Caddy داخلی لازم است.
  3. کد پروژه را روی سرور بگذارید (مثلاً با git clone) و وارد پوشهٔ آن شوید.

۵ ساخت فایل .env

$ cp .env.example .env $ chmod 600 .env

سپس با ویرایشگر متن (نه با دستورهایی که مقدار را در تاریخچهٔ ترمینال می‌گذارند) فایل را کامل کنید:

متغیرمقدار
APP_URLمبدأ عمومی دقیق با HTTPS، مثلاً https://password.example.local
APP_HOSTفقط نام میزبانِ همان مبدأ، مثلاً password.example.local — باید با APP_URL بخواند
TRUENAS_URLآدرس HTTPS NAS فقط برای بک‌اند، مثلاً https://truenas.home.local — بدون مسیر API
TRUENAS_API_KEYکلید ساخته‌شده در گام ۲
SESSION_SECRETحداقل ۴۸ نویسهٔ تصادفی، مثلاً با openssl rand -hex 48
POSTGRES_PASSWORDهگز تصادفی حداقل ۶۴ نویسه (openssl rand -hex 32)؛ Compose خودش رشتهٔ اتصال را می‌سازد. در استقرار مجدد روی حجم موجود، رمز قبلی را نگه دارید.
NODE_EXTRA_CA_CERTSبرای CA داخلی از حالت کامنت خارج کنید: /usr/local/share/ca-certificates/nas/nas-ca.crt

متغیرهای PASSWORD_LINK_TTL_MINUTES، PASSWORD_MIN_LENGTH و نرخ‌ها مقادیر پیش‌فرض معقول دارند؛ در صورت نیاز به سیاست سازمانتان تغییرشان دهید. TRUST_PROXY را دست نزنید — Compose خودش برای پشت Caddy تنظیمش می‌کند.

.env هرگز commit یا اسکرین‌شات نشود و در پیام یا تیکت قرار نگیرد. خطاهای راه‌اندازی فقط نام متغیر معیوب را می‌گویند، نه مقدارش را.

۶ آماده‌سازی حافظهٔ ساخت آفلاین

Dockerfile از بایگانی‌های npm از پیش دانلود و راستی‌آزمایی‌شده استفاده می‌کند؛ deploy.sh آن‌ها را نمی‌سازد. برای معماری سرور خود (x64 یا arm64) یک‌بار اجرا کنید — این مرحله از اینترنت دانلود می‌کند:

$ python3 scripts/prepare-build-cache.py --arch x64

یا از راهنمای تعاملی:

$ scripts/setup-host.sh --check # گزارش آمادگی بدون نمایش هیچ مقدار محرمانه $ scripts/setup-host.sh --prepare-cache x64

برای راه‌اندازی پایگاه‌داده در محل بدون اینترنت: حافظهٔ npm به‌تنهایی کافی نیست؛ ساخت Docker به ایمیج پایه، بسته‌های Debian و موتور Prisma هم نیاز دارد. روی دستگاه متصل به اینترنت با معماری یکسان با سرور و سورس نسخهٔ موردنظر، فایل محلی .env را از نمونه بسازید و برای اعتبارسنجی Compose یک POSTGRES_PASSWORD آزمایشی و غیرمحرمانه قرار دهید. پس از آماده‌سازی حافظهٔ بالا اجرا کنید:

$ export APP_HOST=localhost $ docker compose build migrate $ docker compose pull db $ images=$(docker compose config --images db migrate) $ docker save -o ../password-desk-db-images.tar $images

بایگانی ایمیج‌ها و فایل‌های پروژه را منتقل کنید، اما .env یا هیچ رمز واقعی را منتقل نکنید. ایمیج ابزارها شامل وابستگی‌ها، موتور Prisma و مهاجرت‌هاست؛ با تغییر مهاجرت‌ها دوباره ساخته و منتقل شود. نام پوشهٔ پروژه را در دو دستگاه یکسان نگه دارید. در استقرار موجود، نام پروژهٔ Compose و حجم پایگاه‌داده را تغییر ندهید. اگر نام‌ها متفاوت‌اند، ایمیج واردشده را با docker tag <imported-tools-image> <destination-tools-image> به نام مورد انتظار مقصد (معمولاً <project>-migrate:latest) برچسب بزنید؛ برای تطبیق ایمیج، نام پروژهٔ موجود را عوض نکنید. دستور APP_HOST=localhost docker compose config --images db migrate نام‌های لازم را بدون نمایش رمزها نشان می‌دهد.

۷ استقرار

در یک ترمینال تعاملی (برای پرسش مدیر اول لازم است) اجرا کنید:

$ scripts/setup-host.sh --deploy

این دستور پس از تأیید شما (تایپ DEPLOY)، پیکربندی Compose را بی‌صدا اعتبارسنجی می‌کند و scripts/deploy.sh موجود را اجرا می‌کند: ساخت ایمیج‌ها، شروع PostgreSQL، اجرای مهاجرت‌ها، پرسش تعاملی نام کاربری و رمز مدیر اول (ورودی مخفی؛ سیاست رمز اعمال می‌شود؛ هیچ رمز پیش‌فرضی وجود ندارد) و سپس شروع اپ و پروکسی با بررسی سلامت.

در سرور بدون اینترنت، با Docker Compose و فایل محلی .env شامل POSTGRES_PASSWORD، ابتدا ایمیج‌های آماده‌شده در گام ۶ را وارد کنید و سپس در ترمینال تعاملی اجرا کنید. برای حجم پایگاه‌دادهٔ موجود، رمز قبلی را نگه دارید:

$ docker load -i /path/to/password-desk-db-images.tar $ ./scripts/setup-db.sh

این دستور فقط از ایمیج‌های محلی استفاده می‌کند؛ هیچ ایمیجی نمی‌سازد یا دانلود نمی‌کند و بررسی به‌روزرسانی Prisma را غیرفعال می‌کند. اگر ایمیجی موجود نباشد، پیش از شروع پایگاه‌داده خطا می‌دهد. در سرور مقصد نیازی به Node یا حافظهٔ ساخت نیست. PostgreSQL شروع می‌شود، مهاجرت‌ها اجرا می‌شوند و نام کاربری و رمز/تأیید رمز مخفی پرسیده می‌شود. این حساب، مدیر اپلیکیشن است؛ نه ابرکاربر PostgreSQL و نه حساب TrueNAS. اجرای دوباره، مدیر و رمز موجود را تغییر نمی‌دهد. اپ و پروکسی شروع یا متوقف نمی‌شوند. اگر ساخت مدیر شکست خورد، مهاجرت‌ها باقی می‌مانند؛ ورودی یا پیکربندی را اصلاح و دستور را دوباره اجرا کنید.

فقط setup-db.sh مسیر آفلاین است. دستور استقرار کامل بالا و حالت‌های deploy.sh همچنان ایمیج می‌سازند و با این تغییر آفلاین نمی‌شوند.

برای اجرای فقط مهاجرت‌ها، بدون ساخت مدیر (این مسیر همچنان ایمیج می‌سازد):

$ ./scripts/deploy.sh --database-only

استقرارهای بعدی، در صورت وجود مدیر، بخش ساخت مدیر را رد می‌کنند و هرگز رمز مدیر موجود را بازنشانی نمی‌کنند. خطای پیکربندی فقط نام متغیرها را می‌گوید.

۸ اعتبارسنجی با حساب آزمایشی

  1. مرورگر را روی APP_URL باز کنید؛ رابط به فارسی و راست‌به‌چپ است (با کلید سرصفحه به انگلیسی برمی‌گردد).
  2. با حساب مدیر ساخته‌شده در گام ۷ وارد /admin شوید.
  3. نام کاربری حساب آزمایشی (مثلاً smb-test از گام ۲)، مدت انقضا (پیش‌فرض ۳۰ دقیقه) و یادداشتی بدون اطلاعات محرمانه را وارد و «ایجاد پیوند یک‌بارمصرف» را بزنید. پیوند را همان‌جا کپی کنید — بعد از بستن، دوباره قابل مشاهده نیست.
  4. در مرورگر/حساب دیگری، پیوند را در یک کانال خصوصی واقعی (مثلاً پیام مستقیم رمزگذاری‌شده) به خودتان بفرستید و بازش کنید.
  5. رمز جدید و تأییدش را وارد کنید و تغییر را ثبت کنید. سپس ورود SMB با همان رمز جدید را جداگانه امتحان کنید. پیوند موفق، بلافاصله بسته می‌شود.
  6. در فهرست پیوندهای اخیر، وضعیت «استفاده‌شده» و رد حسابرسی مربوطه را ببینید. عمل لغو روی یک پیوند فعال دیگر را هم آزمایش کنید.

۹ کار روزمره و امنیت پیوندها

  • برای هر درخواست کاربر، پیوند کوتاه‌عمر بسازید (۳۰ دقیقه پیش‌فرض) و از کانال خصوصی مطمئن بفرستید؛ در چت عمومی، ابزارهای آنالیتکس‌دار یا سیستم تیکت paste نکنید.
  • صفحهٔ عمومی هرگز نام کاربری یا آدرس NAS را نشان نمی‌دهد؛ کاربر فقط رمز جدید را وارد می‌کند.
  • پیوند مشکوک به افشا را فوراً «لغو» کنید. پیوندهای منقضی/استفاده‌شده/لغوشده قابل ارسال مجدد نیستند.
  • ورود به /admin را با رمز قوی محافظت کنید؛ برای استقرارهای حساس، دسترسی به مسیر مدیر را با VPN محدود کنید (MFA داخلی وجود ندارد).
  • هیچ «ورود رمز فعلی» وجود ندارد — این تغییرِ آگاهانهٔ اپراتور است؛ امنیت کانال ارسال پیوند جایگزین آن است.

۱۰ پشتیبان‌گیری و بازیابی

پایگاه‌داده شامل هش رمز مدیر، هش نشست‌ها، نام کاربران و تاریخ حسابرسی است. به مقصد رمزگذاری‌شده و با دسترسی محدود پشتیبان بگیرید:

$ umask 077 $ docker compose exec -T db pg_dump -U password_service -d password_service -Fc > /secure-backups/password-service.dump

پیش از بازیابی: جلوی ورود اپ را بگیرید، در پایگاه‌دادهٔ تمیز با pg_restore بازگردانی و مهاجرت‌ها را اعمال کنید، همهٔ Sessionها را حذف و همهٔ پیوندهای فعال قبلی را لغو کنید (بکاپ قدیمی‌تر از مصرف/لغو است و می‌تواند پیوند بسته‌شده را زنده کند)، سپس دسترسی را باز کنید.

۱۱ رفع اشکال

  • خطای پیکربندی هنگام راه‌اندازی: فقط نام متغیر معیوب اعلام می‌شود؛ همان را در .env درست کنید. مقادیر نمونهٔ .env.example عمداً رد می‌شوند.
  • خطای عمومی تغییر رمز: وضعیت حساب SMB محلی، اعتماد گواهی NAS، انقضا/دسترسی کلید API و نسخهٔ دقیق سرور را بررسی کنید. برای تشخیص، هرگز ثبت محتوا (payload logging) را روشن نکنید.
  • «نیاز به بررسی»: عملیاتی در جریان یا نامشخص است. اپ را متوقف کنید، وضعیت واقعی حساب را از کانال مدیریتی مطمئن بررسی کنید و طبق راهنمای README عمل کنید؛ هرگز دوباره تلاش نکنید تا روشن نشود تغییر انجام شده یا نه.
  • 403 روی فرم‌ها: APP_URL باید دقیقاً با مبدأ عمومی یکی باشد.
  • 429 برای چند کاربر: احتمالاً همه از یک آی‌پی شمارش می‌شوند؛ دسترسی مستقیم به اپ باید مسدود باشد و فقط Caddy جلوی آن باشد.
  • ساخت مدیر ممکن نیست: ترمینال تعاملی به‌کار ببرید و اول مهاجرت‌ها را اجرا کنید؛ نام کاربری تازه‌ای انتخاب کنید.
